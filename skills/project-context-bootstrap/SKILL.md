# Project Context Bootstrap

This seed skill creates or repairs a repository's durable agent context system. It derives the structure from project evidence, then establishes one project-local method for routine context evolution.

## Governing source

Read `references/kernel-principles.md` before designing or changing the target context system. Apply all four principles as independent constraints.

## Operating premise

Treat the target agent as a capable new engineer. Give it compact project-specific orientation, clear owners, reliable routes, task methods, and direct access to evidence. Let code, tests, schemas, runtime records, and external authorities retain facts they already express well.

Choose paths, document types, context planes, and skill boundaries from the repository's existing conventions and actual coordination needs. Establish a new structure only where the project lacks a coherent owner or route. Repository-native files and existing validation tooling form the default infrastructure.

## Bootstrap method

1. **Establish the outcome.** State which future agent tasks should become safer, faster, or more consistent and identify the current context failure.
2. **Perform project archaeology.** Inspect the repository entry points, architecture, modules, public interfaces, build and test systems, configuration, deployment, data boundaries, risk surfaces, plans, history, and recurring task patterns. Record evidence before designing the context shape.
3. **Derive the knowledge model.** Identify the durable categories this project actually needs, such as governance, product contracts, architecture, domain meaning, plans, operations, risk, and evidence. Keep the category set as small as reliable execution allows.
4. **Assign canonical owners.** Give each context-worthy truth one narrow owner. Preserve coherent existing owners. Convert parallel explanations into routes or scope-specific local applications. Let cheaply recoverable mechanics remain in code and executable evidence.
5. **Build the onboarding route.** Create or refine one compact project entry. Route each task horizontally to the relevant standard, skill, product contract, plan, risk owner, or evidence source. Keep the path from entry to owner short.
6. **Establish the intended context and change owner.** For durable capability or behavior work, place the target state in one explicit plan or proposal while current owners continue to describe the accepted system.
7. **Generate project skills.** Create skills for recurring, high-risk, fragile, or project-specific procedures. Each skill owns one trigger-specific method, reads the narrowest relevant owners, and carries proportionate acceptance evidence. Prefer local project skills over generic narration.
8. **Create the evolution capability.** Establish one project-local skill as the sole procedure for constructing, consolidating, relocating, simplifying, and iterating the context system. It applies the bundled principles, maintains routes and owners, and closes stale sources in the same change.
9. **Add semantic regression evidence.** Use the project's existing test stack or small standard-library checks to protect critical routes, owner uniqueness, required metadata, and context-first ordering. Test semantic anchors with deliberate restraint; human review remains responsible for meaning beyond executable checks.
10. **Validate with a cold start.** Approach the repository from a fresh-agent perspective. Confirm that the entry reveals the right owners, the selected context supports sound judgment, and a representative task can proceed from repository evidence alone.
11. **Implement or reconcile the code.** Follow the established target context, validate behavior, promote accepted meaning into current owners, close temporary change state, and retire stale routes together.

## Change-state handling

Classify each context-worthy change before dependent work expands:

- **Aligned:** proceed through the normal task skill and preserve agreement among owners, implementation, tests, and evidence.
- **Context ahead:** implement toward the explicit change owner; keep current owners current until acceptance, then promote the accepted meaning.
- **Implementation ahead:** inspect implementation and evidence, create the missing reconciliation owner, determine durable intent, and align current owners before closure.
- **Diverged:** identify the intended durable behavior and canonical owner, resolve the semantic conflict, then continue dependent implementation.

## Evolution loop

At the end of a material task, inspect whether the work revealed a durable fact, recurring method, ownership boundary, onboarding gap, or failed assumption. Promote evidence-backed knowledge into the narrowest owner or project skill. Keep one-off observations in task evidence or history. Re-run the cold-start route after structural context changes.

## Acceptance

The bootstrap is complete when:

- a new agent can find the relevant owner from one compact entry;
- durable facts have clear canonical owners and routes carry navigation or local application only;
- shared prose foregrounds intended outcomes and precise responsibility;
- current truth, target change, implementation, and evidence have explicit coordination states;
- recurring project procedures have discoverable skills;
- the project owns one context-evolution method;
- validation protects the highest-value context invariants;
- the resulting system fits the project and remains independently understandable after the seed completes.
